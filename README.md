# UptimePulse — Сервис мониторинга доступности сайтов

Сквозной проект по дисциплине **«Разработка серверных приложений»**.  
**Вариант 23:** Сервис мониторинга доступности сайтов (Uptime Monitor).

---

## 📌 О проекте
**UptimePulse** — платформа для автоматизированного периодического мониторинга работоспособности и производительности веб-ресурсов (сайтов, микросервисов, REST API).

---

## 📂 Структура репозитория (Clean / Layered Architecture)
```text
.
├── cmd/
│   └── app/
│       └── main.py          # Точка входа в приложение (запуск сервера)
├── internal/
│   ├── config/              # Загрузка конфигурации из .env (Config loader)
│   ├── controller/          # Transport / HTTP Handlers (Слой представления)
│   ├── service/             # Business Logic Layer (Слой бизнес-логики)
│   └── repository/          # Data Access Layer (Слой работы с БД)
├── .env.example             # Шаблон переменных окружения (в Git)
├── .gitignore               # Исключения для Git (скрывает .env, venv, кэш)
├── openapi.yaml             # Спецификация REST API OpenAPI 3.0 (из ЛР2)
├── ARCHITECTURE.md          # Архитектурный отчет (Use Cases, C4, ERD)
├── requirements.txt         # Список зависимостей проекта
└── README.md
```

---

## 🚀 Быстрый старт и запуск

### 1. Установка зависимостей
```bash
pip install -r requirements.txt
```

### 2. Настройка переменных окружения
Скопируйте шаблон `.env.example` в локальный файл `.env`:
```bash
cp .env.example .env
```

### 3. Запуск приложения
```bash
python cmd/app/main.py
```
Сервер запустится по адресу: `http://localhost:8080`.

### 4. Проверка работоспособности (Health Check)
```bash
curl http://localhost:8080/api/v1/health
```

Ожидаемый ответ (`200 OK`):
```json
{
  "status": "pass",
  "app_name": "UptimePulse API",
  "version": "1.0.0",
  "environment": "development"
}
```

Интерактивная документация Swagger UI доступна по адресу:  
`http://localhost:8080/docs`

## ❓ Ответы на контрольные вопросы (Лабораторная работа №3)

#### 1. Почему слой бизнес-логики (Service Layer) не должен знать о деталях HTTP-запросов (например, о структуре JSON-тела или заголовках)?
* **Принцип разделения ответственности:** задача Service Layer — реализовывать бизнес-правила предметной области, а не парсить HTTP-заголовки или сетевые пакеты.
* Если сервис зависит от деталей HTTP, его невозможно будет переиспользовать в других сценариях (например, вызов из CLI-утилиты, фонового воркера по расписанию или gRPC). Сервис должен работать только с чистыми доменными объектами и структурами данных языка.

#### 2. В чем опасности хранения секретов (пароли к БД, API-ключи) непосредственно в исходном коде программы?
* **Утечка учетных данных:** при попадании кода в публичный или командный Git-репозиторий пароли становятся доступны третьим лицам.
* **Невозможность безопасного деплоя под разные среды:** пароли и хосты БД на локальной машине разработчика (`development`) и на боевом сервере (`production`) должны быть разными. Если они захардкожены в коде, проект невозможно безопасно развернуть в продакшене.

#### 3. Зачем нужен файл .env.example, если сам файл .env находится в .gitignore?
* Сам файл `.env` содержит реальные приватные пароли и ключи, поэтому скрыт от системы контроля версий.
* Файл **`.env.example`** служит живой документацией и шаблоном: он показывает другим разработчикам и системам CI/CD, какие именно переменные окружения требуются приложению для корректного запуска.

#### 4. Для чего в микросервисной и серверной архитектуре используется эндпоинт Health Check (/health)?
* Для мониторинга и автоматической оркестрации (Kubernetes, Docker Swarm, Nginx / AWS Load Balancer). Балансировщики регулярно опрашивают `/health`: если сервис завис или исчерпал ресурсы и не вернул `200 OK`, трафик на него прекращается, а упавший контейнер автоматически перезапускается.

#### 5. Что такое инверсия зависимостей (Dependency Inversion) и как она помогает связывать между собой слой API, слой сервисов и слой репозиториев?
* **Принцип инверсии зависимостей:** модули верхних уровней не должны зависеть от низкоуровневых модулей; оба уровня должны зависеть от абстракций (интерфейсов).
* Слой сервисов объявляет интерфейс доступа к данным (какие методы ему нужны), а слой репозиториев его реализует. Это позволяет подменять реальную базу данных (например, PostgreSQL) тестовыми моками (mock) без изменения кода бизнес-логики.
